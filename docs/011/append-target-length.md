# 续写字数档位需求文档

## 背景

本文档对应 `011` 主题：续写模式下允许用户指定本轮生成的目标字数。

当前故事写作链路里，`append` 续写使用固定的长度要求，用户无法主动控制“这轮想写短一点还是长一点”。这会带来两个问题：

- 用户在不同创作节奏下缺少长度控制能力。
- 系统无法记住用户偏好的续写长度，每次都只能使用同一套默认策略。

本期目标是在不改动 `create / rewrite / dialogue` 行为的前提下，只为 `append` 续写增加一个简单、稳定、可记忆的长度档位能力。

## 目标

- 用户在续写抽屉里可以选择本轮续写的目标字数档位。
- 前端只提供 `250 / 500 / 750 / 1000` 四个固定档位，不提供自由输入。
- 服务端续写契约接收单值字数参数，并对 `100-1200` 做强校验。
- 当前用户的长度偏好通过 `localStorage` 记忆，不区分故事线。
- 首次使用或本地缓存无效时，默认使用 `1000` 字档。

## 非目标

- 不为 `create` 新建故事增加字数选择。
- 不为 `rewrite` 或 `dialogue` 增加字数选择。
- 不提供自定义输入框让用户手填任意字数。
- 不按故事线分别记忆长度偏好。
- 不把长度偏好保存到服务端数据库。
- 不对模型输出做生成后截断、补写或因长度偏差自动重试。

## 已确认决策

- 本期迭代编号使用 `011`。
- 本期只覆盖 `append` 续写模式。
- 服务端契约采用“单值字数”语义，而不是 `min/max` 显式区间。
- 前端四档固定数值映射为：`250`、`500`、`750`、`1000`。
- 前端按钮文案使用语义标签：`短`、`中`、`长`、`很长`。
- 默认档位为 `1000`，以尽量贴近当前默认续写体验。
- 用户一旦切换档位，就立即写入 `localStorage`。
- 本地记忆按登录用户隔离，不按故事线隔离。
- 如果 `localStorage` 中的值损坏、越界或不在支持档位内，前端静默回退到 `1000`，并覆盖坏值。
- 字数要求是 LLM 的“目标长度约束”，不是严格长度承诺。

## 用户故事

### 已有故事线续写

1. 用户进入已有故事线详情页。
2. 用户点击「续写」，打开底部抽屉。
3. 抽屉内展示 4 个字数档位，默认选中当前用户最近一次使用的档位；若没有历史值则选中 `1000`。
4. 用户切换字数档位，系统立即记住该选择。
5. 用户填写续写指令并提交。
6. 服务端按本次选择的目标字数生成续写正文。

### 跨故事线复用偏好

1. 用户在故事线 A 中把续写长度切到 `500`。
2. 用户切换到故事线 B，再次打开续写抽屉。
3. 系统仍默认选中 `500`，因为长度偏好属于“用户级偏好”，不属于“故事级偏好”。

### 多用户隔离

1. 浏览器中依次登录两个不同用户。
2. 每个用户都应看到自己最近一次选择的档位。
3. 不同用户之间的本地偏好不能互相覆盖。

## 产品交互

### 续写抽屉

- 只在 `append` 续写抽屉中展示字数档位选择器。
- 建议把档位选择器放在「续写指令」输入框上方，作为同一表单的一部分。
- 前端按钮文案展示为：`短`、`中`、`长`、`很长`。
- 四个语义档位的固定映射分别为：
  - `短` => `250`
  - `中` => `500`
  - `长` => `750`
  - `很长` => `1000`
- 四档单选，同一时刻只能选中一个。
- 切换档位不需要额外确认。
- 关闭抽屉不会撤销刚刚切换的档位，因为该行为属于“用户偏好修改”。

### 默认值与恢复

- 初次使用时，默认选中 `很长` 档，对应 `1000`。
- 页面刷新后，应恢复当前用户最近一次选择的档位。
- 切换故事线后，应继续沿用当前用户最近一次选择的档位。
- 登出后重新登录同一用户，应恢复该用户的历史档位。
- 如果是另一个用户登录，则读取该用户自己的档位记录。

### 生成行为

- 用户点击「生成续写」时，前端把当前选中的目标字数一并提交。
- 成功、失败、取消后，都不重置当前用户的长度偏好。
- 后续再次打开续写抽屉时，仍显示最近一次记住的档位。

### 异常回退

- 若本地缓存缺失、不是数字、超出 `100-1200`，或不属于本期支持的四档，前端不弹错误。
- 前端直接回退到 `很长` 档（对应 `1000`），并把坏值覆盖为有效默认值。

## 共享契约

本期仅扩展 `StoryContinueAppendPayload`；其他写作模式的 payload 保持不变。

```ts
export const StoryContinueAppendPayloadSchema = z
  .object({
    mode: z.literal("append"),
    storylineId: StorylineIdSchema,
    instruction: z.string().trim().min(1).max(8_000),
    targetLength: z.number().int().min(100).max(1_200),
  })
  .strict();
```

约束说明：

- `targetLength` 为单个整数，表示本轮续写的目标字数。
- 服务端必须强校验：
  - 只能是整数；
  - 最小 `100`；
  - 最大 `1200`。
- 前端本期只会提交 `250 | 500 | 750 | 1000` 四个值。
- 服务端保留 `100-1200` 的完整接收区间，为未来可能的更多档位或其他入口预留空间。

## 服务端需求

### 校验

- `append` 续写请求新增 `targetLength` 必填字段。
- WebSocket 消息和其他共享 schema 消费方都必须复用同一份 Zod 契约进行强校验。
- 当 `targetLength` 缺失、非整数、低于 `100` 或高于 `1200` 时，服务端必须拒绝请求。
- 现有错误语义保持一致，按现有非法 payload 处理链路返回错误。

### Writer Prompt

- `append` 续写不再使用固定的单一长度要求。
- 服务端需要把本轮 `targetLength` 注入续写 Writer 的长度约束中。
- `create`、`rewrite`、`dialogue` 的现有 Prompt 行为保持不变。

### 输出策略

- 长度档位是“尽量接近”的目标，而不是严格命中。
- 服务端不因为结果偏长或偏短而自动截断正文。
- 服务端不因为结果偏长或偏短而自动触发补写或重试。
- 本期核心目标是让不同档位对生成长度产生稳定、可感知的方向性影响，而不是做严格长度控制。

## 前端需求

### 页面范围

- 仅在故事线详情页的 `append` 续写抽屉接入本能力。
- `create` 页面不展示该控件。
- `rewrite` 抽屉不展示该控件。
- `dialogue` 抽屉不展示该控件。

### 状态与存储

- 前端需要维护当前选中的 `append` 目标字数状态。
- 本地存储按用户维度隔离，推荐基于 `userId` 做 key 命名空间。
- 本地存储的值只允许落四个受支持档位之一。
- 用户切换档位时立即写入本地存储，而不是等提交成功后再写。

### 提交

- 当用户提交 `append` 续写时，请求 payload 必须包含当前选中的 `targetLength`。
- 当用户提交 `rewrite` 或 `dialogue` 时，不应携带该字段。

## 验收标准

- 用户在 `append` 续写抽屉中能看到 `短 / 中 / 长 / 很长` 四个档位。
- 四个语义档位分别固定映射到 `250 / 500 / 750 / 1000`。
- 首次使用或本地值无效时，默认选中 `很长` 档（映射 `1000`）。
- 用户切换档位后，刷新页面或切换到另一条故事线，仍能看到同一档位被选中。
- 同一浏览器的不同登录用户拥有彼此独立的长度偏好。
- `append` 请求会携带 `targetLength`，且服务端对 `100-1200` 做强校验。
- 对非法 `targetLength`，服务端会拒绝请求，不进入正常生成流程。
- `create / rewrite / dialogue` 的交互和契约不因本期需求发生变化。
- 系统对长度档位采用 best-effort 策略：用户可感知不同档位带来的长度差异，但系统不承诺严格命中字数，也不做生成后裁切。

## 风险与取舍

### 长度无法严格命中

LLM 天然不适合严格长度控制。本期采用 best-effort，是为了避免引入截断破坏语义、补写打断节奏、重试增加成本这三类更明显的问题。

### 本地偏好不跨设备同步

长度偏好保存在 `localStorage`，所以只对当前浏览器生效。这样实现简单、风险低，但用户换设备后不会自动同步。

### 首轮新建仍沿用现有长度策略

本期只覆盖 `append`。这意味着用户在首轮 `create` 时仍沿用现有默认生成长度；只有进入已有故事线后的续写，才能主动选择档位。
